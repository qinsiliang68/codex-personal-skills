# Repo File Management

## Prime Rule

Treat the repository as an asset management system, not a temporary workbench.

Every file that enters the repository must have:

- identity: what it is
- owner: which module or department owns it
- source: where it came from
- consumer: who or what reads it
- lifecycle: keep, regenerate, archive, or delete
- verification: how to prove it is correct
- git policy: commit, ignore, or keep local only

If those answers are unclear, do not create the file.

This skill complements development skills such as `repo-development-protocol`.
Use this skill for asset placement and repository hygiene. Use development
protocols for code, tests, TDD, DAA, and commit discipline.

## Hard Stop Conditions

Stop before writing when any of these is true:

- the target path does not have a clear owner
- the file is a temporary convenience artifact with no cleanup rule
- a new top-level folder would duplicate an existing department
- generated output would be mixed with human-authored truth
- model predictions would be mixed with human labels
- immutable parser evidence or source materials would be overwritten
- a script would decide human labels or rewrite truth assets
- a large asset would be committed without manifest, count, and hash evidence
- the user has not explicitly approved destructive cleanup

## Before Creating Any File Or Folder

Answer this checklist in your own reasoning before acting:

1. Why does this file exist?
2. Which existing directory owns it?
3. Is it source truth, human truth, generated output, log, test fixture, review package, model artifact, or temporary waste?
4. Who imports, reads, or reviews it?
5. Is it reproducible from source and script?
6. Does it need a README, manifest, or log entry?
7. Should it be committed, ignored, kept on Desktop, or deleted after use?
8. Could it confuse the next AI agent?

If a file could confuse the next AI agent, it needs a better home, a manifest,
or deletion.

## Folder Responsibility Boundaries

Folders must be departments with clear responsibility, not storage buckets.

Each durable folder must have exactly one primary responsibility:

- source materials
- parser evidence
- cleaned outputs
- structured outputs
- retrieval assets
- MCP packaging assets
- model-training assets
- logs
- tests or fixtures
- discarded files

Do not put one asset in several possible homes. Choose the folder whose
responsibility owns the asset, then document that choice if it is not obvious.

Do not create a folder whose purpose overlaps an existing folder. If two folders
would both answer "generated outputs", "temporary files", "training data", or
"review artifacts", stop and merge the design into one responsibility map.

Folder names should describe the department, not the moment:

```text
Good: 01_training_datasets, 03_evaluation, parsing, recycle_bin
Bad: new, old, temp, final, fixed, use_this, misc, stuff
```

If a folder's responsibility changes, update its README or manifest in the same
change. Do not leave the old meaning for the next AI agent to guess.

## Asset Classes

Use these classes for any repository.

| Class | Meaning | AI write rule |
|---|---|---|
| Source truth | original PDFs, DOCX, raw source data, locked customer inputs | never overwrite; copy before processing |
| Human truth | manual labels, reviewed annotations, approved schemas, curated manifests | edit only by explicit task; small patch; verify; commit separately |
| Parser evidence | raw parser output, page evidence, OCR traces, source hashes | immutable after creation; later stages read only |
| Derived dataset | JSONL, CSV, processed train/dev/test data generated from truth | generated by scripts; include manifest and source hashes |
| Runtime log | command logs, events, metrics, failures | append or create under log areas; never mix with source |
| Review package | human-readable extracts, zip packages, inspection views | local/Desktop unless repo policy says otherwise |
| Experiment output | predictions, checkpoints, metrics, reports | keep under documented experiment/model areas; manifest required |
| Temporary waste | scratch checks, one-off snippets, abandoned attempts | Desktop/temp or recycle area; not committed |

## Protected Path Rules

### Never edit directly

```text
review_artifacts/01_parsed/
corpus_current/ original source files
```

Read them, copy from them, hash them, count them, compare them. Do not mutate
them unless the user explicitly asks for source-material curation.

### Human annotation truth

```text
review_artifacts/06_model_training/00_parsed_annotation_workspace/
```

Manual annotation files are human truth. Edits must be:

- small and reviewable
- label-only unless the user explicitly asks to correct text
- one document and one parser per commit when committing
- verified by opening/closing tag integrity and source-text preservation

Scripts may extract, count, validate, and generate JSONL from labels. Scripts
must not decide labels or insert semantic labels.

### Generated training datasets

```text
review_artifacts/06_model_training/01_training_datasets/
```

Generated datasets must include a manifest with:

- dataset id
- created time
- source annotation paths
- source hashes
- script or command
- git commit
- parser set
- label set
- split policy
- record counts
- document counts

### Model runs and evaluation

```text
review_artifacts/06_model_training/02_model_runs/
review_artifacts/06_model_training/03_evaluation/
```

Every serious model run needs a manifest with config path, dataset id, code
commit, metrics, checkpoint location, and intended use. Large checkpoints should
not be committed unless the repository policy explicitly says to commit them.

## No Random Folder Rule

Before creating a new folder, prefer an existing department. A new folder is
allowed only when all are true:

- no existing department fits
- the folder has a stable owner
- the folder has a clear lifecycle
- a README or manifest explains it
- the user has approved the new category or the repository already documents it

New top-level folders are high-risk. Ask or stop unless the user explicitly
requested that structure.

## Skill Responsibility And Placement

Skills must also have clear responsibility. Do not build one giant skill that
tries to govern unrelated work.

Use separate skills for separate duties:

```text
repo-development-protocol
  Code changes, DAA, TDD, tests, commits, docs sync for development work.

repo-file-management
  File placement, asset identity, lifecycle, manifests, protected paths,
  cleanup rules, no random folders, and repository hygiene.

parser-output-manual-annotation
  Human annotation rules for parser-output Markdown and training labels.
```

Skill folders belong under:

```text
%USERPROFILE%\.codex\skills\<skill-name>\
```

Each skill folder should contain one `SKILL.md` with one clear frontmatter
`name`. Do not store several unrelated skills in one folder, and do not store
draft skill files in project repositories unless the repository itself is a
skill project.

When a new recurring rule appears, decide whether it belongs in an existing
skill or deserves a new skill. Put it where future agents will naturally look,
not wherever the current conversation happens to be.

## Temporary And Desktop Artifacts

Use Desktop for human handoff packages, review zips, and temporary exports that
the user wants to inspect outside the repo.

Rules:

- Desktop packages are not training source.
- Include a manifest when packaging data for experts or transfer.
- Include counts and hashes.
- Do not copy Desktop packages back into the repository unless the user asks.
- Delete obsolete Desktop review folders only when the user asks or when their
  lifecycle is explicitly temporary and replacement is confirmed.

## Temporary Artifact Lifecycle

Temporary artifacts must not become mystery assets.

Every temporary artifact must have one of these outcomes:

- delete after use
- replace an older artifact and make the older artifact obsolete
- move uncertain leftovers to `recycle_bin/`
- promote to a durable department with README or manifest
- keep as append-only evidence because the directory explicitly allows it

For temporary packages or review folders, record at least:

```text
purpose:
created_at:
source:
replaced_by:
delete_after:
lifecycle: temporary|obsolete|promoted|append-only-evidence
```

Do not keep growing piles of temporary review folders just because they might be
useful. If a newer package supersedes an older one, either delete the older one,
mark it obsolete in its manifest, or move it to the recycle area after user
approval when needed.

Only these categories may be intentionally append-only:

- runtime logs under `log/`
- audit trails
- manifests for committed asset batches
- model/evaluation run records that have unique run ids
- user-approved archival evidence

Append-only does not mean messy. Append-only assets still need dates, run ids,
counts, hashes, and a README or manifest explaining retention.

## Manifest Requirements

Any asset batch needs a manifest when it contains more than one file, will be
shared, will be committed, or may be used for training/evaluation.

Minimum manifest fields:

```json
{
  "asset_id": "",
  "created_at": "",
  "created_by": "codex-or-user",
  "purpose": "",
  "source_paths": [],
  "source_hashes": {},
  "output_paths": [],
  "counts": {},
  "script_or_command": "",
  "git_commit": "",
  "verification": [],
  "lifecycle": "keep|regenerate|temporary|archive",
  "notes": ""
}
```

For zips, report zip path, file count, byte size, and sha256.

## README Rules

Every non-obvious durable directory needs a README answering:

1. What belongs here?
2. What does not belong here?
3. Which files are source truth versus generated?
4. How is this directory generated or maintained?
5. What must be updated when contents change?

Do not create README noise for throwaway Desktop packages unless the package
needs human handoff instructions. Use a short `README.txt` or manifest instead.

## Documentation Sync Gate

Documentation is part of file management.

Update the nearest README, manifest, or project map when any of these change:

- directory responsibility
- source-truth location
- generated-output location
- input or output contract
- naming rule
- cleanup or retention rule
- command that creates an asset
- dataset, split, model, or evaluation artifact
- parser, cleaning, structuring, retrieval, or MCP stage responsibility
- protected path policy

If no documentation update is needed, state why in the final response.

For every asset-related task, report one of:

```text
Docs updated: <paths>
Docs not updated because: <reason>
```

Do not silently change structure and leave the next AI agent to infer the new
rules from file names.

## Cleanup Rules

Cleanup is required, but deletion must be safe.

- Delete obvious local junk only when it is clearly not a project asset.
- Move uncertain repo files to the documented recycle area instead of deleting.
- Do not keep obsolete files because of fear; classify them.
- Do not create `backup`, `old`, `new`, `fixed`, `final`, or `use_this` files.
- Before deleting or moving many files, list the target paths and confirm they
  are inside the intended directory.

For this repository, use:

```text
recycle_bin/
```

not a new archive folder.

## Git Policy

Use commits as rollback points.

- Commit one semantic asset unit at a time.
- Prefer one document and one parser per annotation commit.
- Do not mix generated datasets with source-code changes unless the task is to
  publish that exact dataset version.
- Do not commit Desktop packages.
- Do not commit large generated artifacts without explicit policy and manifest.
- Before committing, run relevant verification and `git diff --check`.

## AI Behavior Rules

Act like a careful junior maintainer with restricted write access.

Do:

- inspect existing structure before placing files
- use existing project conventions over generic templates
- preserve protected source and evidence
- create manifests for batches
- keep diffs small and reviewable
- explain what was created, why, and how to remove or regenerate it

Do not:

- create convenience folders because they feel useful
- hide temporary files in the repo
- mix predictions with human truth
- overwrite parser evidence
- rewrite whole annotated documents when a label patch is enough
- use scripts to make semantic annotation decisions
- leave mystery artifacts for the next AI agent

## Final Response Requirements

After repository asset work, report:

```text
Created or changed:
Protected truth touched:
Generated assets:
Manifests or README updates:
Verification:
Git status or commit:
Cleanup / remaining lifecycle:
```

If no files were changed, say that explicitly.
